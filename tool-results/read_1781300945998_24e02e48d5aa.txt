    58→### MEJORA sesion 19: Air Intra Batched Sync (evita timeout de Vercel)
    59→- **Problema:** El sync completo de Air Intra (~7,500 productos, 16 paginas de 500) puede tardar 30-60+ segundos, excediendo el limite de 60s de Vercel Hobby plan para serverless functions
    60→- **Solucion:** Sync por lotes (batched) - divide la sincronizacion en chunks de 4 paginas (~2,000 productos, ~10-15s por lote)
    61→- **Arquitectura:**
    62→  1. Primer call: Login + lote 1 (paginas 0-3). Retorna `hasMore: true`, `nextPage: 4`, `token`, `exchangeRate`
    63→  2. Calls subsiguientes: Frontend envia `batch: { startPage, endPage, token, exchangeRate }` para cada lote
    64→  3. Finalize step: Despues de todos los lotes, frontend envia `batch: { token, exchangeRate, finalize: true }` que ejecuta syp sync, recategorizacion, recovery, y actualiza lastSyncAt
    65→- **Backend:** `syncAirIntraBatch()` y `syncAirIntraFinalize()` en `src/app/api/admin/suppliers/sync/route.ts`
    66→- **Frontend:** `handleSync()` en `src/app/admin/proveedores/page.tsx` - orquesta los lotes automaticamente con barra de progreso
    67→- **vercel.json:** `maxDuration` corregido a 60 (antes decia 300, pero Hobby plan limita a 60s)
    68→- **PAGES_PER_BATCH:** 4 (constante, 4 x 500 = 2,000 productos por lote)
    69→- **Compatibilidad:** Invid y Elit siguen usando sync completo (no necesitan batched, son mas chicos)
    70→
    71→### MEJORA sesion 18: Sync robusto de Air Intra - Verificacion doble + post-sync check
    72→- **Problema de fondo:** El sync de Air Intra pierde productos cuando el JSON se corrompe por PHP notices. Incluso cuando `JSON.parse` tiene exito, algunos productos pueden perderse silenciosamente
    73→- **Mejora 1 - Verificacion doble:** `extractProductsFromCorruptedJson` ahora se ejecuta SIEMPRE (no solo como fallback). Despues del parse standard, compara la cantidad de productos extraidos vs parseados. Si el extractor encuentra mas productos, los recupera y los agrega al array de productos. Esto atrapa productos que se pierden cuando PHP notices corrompen el JSON entre objetos

   199→- **Campos:** `salePrice REAL`, `saleStart TEXT`, `saleEnd TEXT` en tabla products

   201→- **Estado actual:** 1 producto con salePrice configurado
   202→- **Admin:** Se gestiona desde el formulario de productos o desde Promociones
   203→
   204→### Formulas de Precio
   205→```
   206→Precio de lista  = costUSD x (1 + ivaRate/100) x (1 + markup/100) x cotizacionDolar
   207→Precio efectivo  = costUSD x (1 + ivaRate/100) x (1 + (markup - cashDiscount)/100) x cotizacionDolar
   208→Precio oferta    = salePrice (si esta dentro del rango de fechas, reemplaza precio de lista)
   209→```
   210→Donde markup, cashDiscount e ivaRate siguen prioridad: Producto individual → Categoría (heredando de padre si no tiene) → Global/Default.

   288→### Sistema de Filtrado de Productos (3 capas - FIX PERMANENTE)
   289→El PC Builder usa **3 capas de defensa** para garantizar que solo productos correctos aparezcan en cada slot:
   290→
   291→| Capa | Mecanismo | Descripcion |
   292→|------|-----------|-------------|
   293→| **1. Inclusion (Whitelist)** | `BUILDER_INCLUDE_PATTERNS` | Cada slot define que palabras clave DEBE tener el nombre del producto (ej: GPU requiere "RTX/GTX/RADEON"). Si no coincide con NINGUN patron, no aparece. **Es la defensa principal: funciona incluso si la categoria en la DB esta mal** |
   294→| **2. Exclusion (Blacklist)** | `BUILDER_EXCLUDE_PATTERNS` | Patrones que excluyen productos no deseados (notebooks en GPU, discos externos en SSD, etc.) |
   295→| **3. Compatibilidad** | `applyCompatibilityFilters` | Filtra por socket (CPU->Mother), DDR (Mother->RAM), wattaje (GPU->PSU) |
   296→
   297→### Por que se desordenaba antes (Causa raiz resuelta)
   298→El problema recurrente tenia 3 causas encadenadas:
   299→1. **Sync categorizaba mal**: El `CATEGORY_KEYWORD_MAP` chequeaba keywords de componentes (RTX, DDR, SSD) ANTES que productos completos (NOTEBOOK, PC ARMADAS). "NOTEBOOK RTX 4060" coincidia con "RTX" primero -> placas-de-video
   300→2. **PC Builder no validaba nombres**: Solo usaba categoria de DB + blacklist chica. No verificaba que el producto realmente fuera lo que dice la categoria
   301→3. **Cada sync traia productos nuevos mal categorizados**: Aunque corrijas manualmente, la proxima sync "contaminaba" otra vez
   302→
   303→### Solucion permanente (implementada sesion 3)
   304→1. **Whitelist en PC Builder**: `BUILDER_INCLUDE_PATTERNS` - cada slot valida el nombre del producto en runtime
   305→2. **Keywords ordenadas en sync**: Productos completos (NOTEBOOK, PC ARMADAS) se chequean ANTES que componentes (RTX, DDR, SSD)
   306→3. **Validacion post-sync automatica**: Despues de cada sync, se corrigen automaticamente productos mal categorizados en TODAS las categorias del PC Builder

   330→- **Bug:** Intel Core Ultra 5 225F con "LGA1851" (sin espacio) en el nombre era detectado como Socket LGA 1700, bloqueando todas las mothers LGA 1851 compatibles
   331→- **Causa raiz:** El regex `/\bS?1851\b/` no matcheaba "LGA1851" porque `\b` no detecta boundary entre "A" y "1" (ambos son word chars). Al fallar, el fallback asignaba "1700" por defecto a todos los Intel

   333→- **Fix 2 - Intel Core Ultra:** Agregada deteccion por modelo: si el nombre contiene "CORE ULTRA", siempre se asigna socket 1851 (Arrow Lake). Se ejecuta antes del fallback a 1700

   612→## Protecciones contra Deploy de Versiones Viejas (IMPLEMENTADO sesion 7)
   613→
   614→### Problema que resolvio
   615→Se pusheo una version vieja del codigo que sobreescribio la version correcta en produccion. La causa raiz fue una carpeta `compucity-repo/` duplicada dentro del proyecto que apuntaba al mismo remote de GitHub.
   616→
   617→### Capa 1: Pre-push hook
   618→- **Archivo:** `githooks/pre-push` (configurado via `git config core.hooksPath githooks`)
   619→- **Funcion:** Antes de cada `git push`, verifica que el local no este atras del remoto
   620→- **Si el local esta atras:** Bloquea el push y muestra instrucciones para hacer `git pull --rebase origin main`
   621→- **Si hay divergencia:** Tambien bloquea y sugiere rebase
   622→
   623→### Capa 2: Script de deploy seguro
   624→- **Archivo:** `scripts/deploy.sh`
   625→- **Uso:** `bash scripts/deploy.sh "mensaje del commit"`
   626→- **Verificaciones:** Rama correcta, fetch remoto, comparar commits, verificar cambios pendientes, solo pushea si todo esta OK
   627→
   628→### Capa 3: Eliminacion del repo duplicado
   629→- **Accion:** Se elimino la carpeta `compucity-repo/` que causaba confusion
   630→- **Proteccion:** Se agrego `compucity-repo/` al `.gitignore` para prevenir recrearlo accidentalmente
   631→
   632→### Workflow recomendado
   633→1. Siempre hacer `git pull --rebase origin main` antes de trabajar
   634→2. Hacer cambios, probar localmente
   635→3. Usar `bash scripts/deploy.sh "feat: descripcion"` para pushear de forma segura
   636→4. Vercel se actualiza automaticamente con el push
