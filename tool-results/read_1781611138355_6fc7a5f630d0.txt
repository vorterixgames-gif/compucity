    75→    75→### MEJORA sesion 19: Air Intra Batched Sync (evita timeout de Vercel)
    76→    76→- **Problema:** El sync completo de Air Intra (~7,500 productos, 16 paginas de 500) puede tardar 30-60+ segundos, excediendo el limite de 60s de Vercel Hobby plan para serverless functions
    77→    77→- **Solucion:** Sync por lotes (batched) - divide la sincronizacion en chunks de 4 paginas (~2,000 productos, ~10-15s por lote)
    78→    78→- **Arquitectura:**
    79→    79→  1. Primer call: Login + lote 1 (paginas 0-3). Retorna `hasMore: true`, `nextPage: 4`, `token`, `exchangeRate`
    80→    80→  2. Calls subsiguientes: Frontend envia `batch: { startPage, endPage, token, exchangeRate }` para cada lote
    81→    81→  3. Finalize step: Despues de todos los lotes, frontend envia `batch: { token, exchangeRate, finalize: true }` que ejecuta syp sync, recategorizacion, recovery, y actualiza lastSyncAt
    82→    82→- **Backend:** `syncAirIntraBatch()` y `syncAirIntraFinalize()` en `src/app/api/admin/suppliers/sync/route.ts`
    83→    83→- **Frontend:** `handleSync()` en `src/app/admin/proveedores/page.tsx` - orquesta los lotes automaticamente con barra de progreso
    84→    84→- **vercel.json:** `maxDuration` corregido a 60 (antes decia 300, pero Hobby plan limita a 60s)
    85→    85→- **PAGES_PER_BATCH:** 4 (constante, 4 x 500 = 2,000 productos por lote)
    86→    86→- **Compatibilidad:** Invid y Elit siguen usando sync completo (no necesitan batched, son mas chicos)
    87→    87→
    88→    88→### MEJORA sesion 18: Sync robusto de Air Intra - Verificacion doble + post-sync check
    89→    89→- **Problema de fondo:** El sync de Air Intra pierde productos cuando el JSON se corrompe por PHP notices. Incluso cuando `JSON.parse` tiene exito, algunos productos pueden perderse silenciosamente
    90→    90→- **Mejora 1 - Verificacion doble:** `extractProductsFromCorruptedJson` ahora se ejecuta SIEMPRE (no solo como fallback). Despues del parse standard, compara la cantidad de productos extraidos vs parseados. Si el extractor encuentra mas productos, los recupera y los agrega al array de productos. Esto atrapa productos que se pierden cuando PHP notices corrompen el JSON entre objetos
    91→    91→- **Mejora 2 - Post-sync verification:** Despues de completar la sync, compara el total de productos sincronizados vs el total en la DB. Si la sincronizacion trajo significativamente menos productos que los que ya existen, genera un warning en el log
    92→    92→- **Mensaje informativo:** El resultado del sync ahora indica si se uso la extraccion de objetos como fallback

   216→   216→### Precio de Oferta (salePrice)
   217→   217→- **Campos:** `salePrice REAL`, `saleStart TEXT`, `saleEnd TEXT` en tabla products
   218→   218→- **Logica:** Si salePrice > 0 y estamos dentro del rango de fechas, se muestra como precio de oferta
   219→   219→- **Estado actual:** 1 producto con salePrice configurado
   220→   220→- **Admin:** Se gestiona desde el formulario de productos o desde Promociones
   221→   221→
   222→   222→### Formulas de Precio
   223→   223→```
   224→   224→Precio de lista  = costUSD x (1 + ivaRate/100) x (1 + markup/100) x cotizacionDolar
   225→   225→Precio efectivo  = costUSD x (1 + ivaRate/100) x (1 + (markup - cashDiscount)/100) x cotizacionDolar
   226→   226→Precio oferta    = salePrice (si esta dentro del rango de fechas, reemplaza precio de lista)
   227→   227→```
   228→   228→Donde markup, cashDiscount e ivaRate siguen prioridad: Producto individual -> Categoria (heredando de padre si no tiene) -> Global/Default.

   306→   306→### Sistema de Filtrado de Productos (3 capas - FIX PERMANENTE)
   307→   307→El PC Builder usa **3 capas de defensa** para garantizar que solo productos correctos aparezcan en cada slot:
   308→   308→
   309→   309→| Capa | Mecanismo | Descripcion |
   310→   310→|------|-----------|-------------|
   311→   311→| **1. Inclusion (Whitelist)** | `BUILDER_INCLUDE_PATTERNS` | Cada slot define que palabras clave DEBE tener el nombre del producto. Si no coincide con NINGUN patron, no aparece. **Es la defensa principal: funciona incluso si la categoria en la DB esta mal** |
   312→   312→| **2. Exclusion (Blacklist)** | `BUILDER_EXCLUDE_PATTERNS` | Patrones que excluyen productos no deseados (notebooks en GPU, discos externos en SSD, etc.) |
   313→   313→| **3. Compatibilidad** | `applyCompatibilityFilters` | Filtra por socket (CPU->Mother), DDR (Mother->RAM), wattaje (GPU->PSU) |

   479→   479→
   480→   480→### Capa 1: Pre-push hook
   481→   481→- **Archivo:** `githooks/pre-push` (configurado via `git config core.hooksPath githooks`)
   482→   482→- **Funcion:** Antes de cada `git push`, verifica que el local no este atras del remoto
   483→   483→- **Si el local esta atras:** Bloquea el push y muestra instrucciones para hacer `git pull --rebase origin main`
   484→   484→
   485→   485→### Capa 2: Script de deploy seguro
   486→   486→- **Archivo:** `scripts/deploy.sh`
   487→   487→- **Uso:** `bash scripts/deploy.sh "mensaje del commit"`
   488→   488→- **Verificaciones:** Rama correcta, fetch remoto, comparar commits, verificar cambios pendientes
   489→   489→
   490→   490→### Capa 3: Eliminacion del repo duplicado
   491→   491→- **Accion:** Se elimino la carpeta `compucity-repo/` que causaba confusion
   492→   492→- **Proteccion:** Se agrego `compucity-repo/` al `.gitignore`
   493→   493→
   494→   494→### Workflow recomendado
   495→   495→1. Siempre hacer `git pull --rebase origin main` antes de trabajar
   496→   496→2. Hacer cambios, probar localmente
   497→   497→3. Usar `bash scripts/deploy.sh "feat: descripcion"` para pushear de forma segura
   498→   498→4. Vercel se actualiza automaticamente con el push
