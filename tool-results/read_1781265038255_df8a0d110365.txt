    55→    55→### MEJORA sesion 19: Air Intra Batched Sync (evita timeout de Vercel)
    56→    56→- **Problema:** El sync completo de Air Intra (~7,500 productos, 16 paginas de 500) puede tardar 30-60+ segundos, excediendo el limite de 60s de Vercel Hobby plan para serverless functions
    57→    57→- **Solucion:** Sync por lotes (batched) - divide la sincronizacion en chunks de 4 paginas (~2,000 productos, ~10-15s por lote)
    58→    58→- **Arquitectura:**
    59→    59→  1. Primer call: Login + lote 1 (paginas 0-3). Retorna `hasMore: true`, `nextPage: 4`, `token`, `exchangeRate`
    60→    60→  2. Calls subsiguientes: Frontend envia `batch: { startPage, endPage, token, exchangeRate }` para cada lote
    61→    61→  3. Finalize step: Despues de todos los lotes, frontend envia `batch: { token, exchangeRate, finalize: true }` que ejecuta syp sync, recategorizacion, recovery, y actualiza lastSyncAt
    62→    62→- **Backend:** `syncAirIntraBatch()` y `syncAirIntraFinalize()` en `src/app/api/admin/suppliers/sync/route.ts`
    63→    63→- **Frontend:** `handleSync()` en `src/app/admin/proveedores/page.tsx` - orquesta los lotes automaticamente con barra de progreso
    64→    64→- **vercel.json:** `maxDuration` corregido a 60 (antes decia 300, pero Hobby plan limita a 60s)
    65→    65→- **PAGES_PER_BATCH:** 4 (constante, 4 x 500 = 2,000 productos por lote)
    66→    66→- **Compatibilidad:** Invid y Elit siguen usando sync completo (no necesitan batched, son mas chicos)
    67→    67→
    68→    68→### MEJORA sesion 18: Sync robusto de Air Intra - Verificacion doble + post-sync check
    69→    69→- **Problema de fondo:** El sync de Air Intra pierde productos cuando el JSON se corrompe por PHP notices. Incluso cuando `JSON.parse` tiene exito, algunos productos pueden perderse silenciosamente
    70→    70→- **Mejora 1 - Verificacion doble:** `extractProductsFromCorruptedJson` ahora se ejecuta SIEMPRE (no solo como fallback). Despues del parse standard, compara la cantidad de productos extraidos vs parseados. Si el extractor encuentra mas productos, los recupera y los agrega al array de productos. Esto atrapa productos que se pierden cuando PHP notices corrompen el JSON entre objetos
    71→    71→- **Mejora 2 - Post-sync verification:** Despues de completar la sync, compara el total de productos sincronizados vs el total en la DB. Si la sincronizacion trajo significativamente menos productos que los que ya existen, genera un warning en el log
    72→    72→- **Mensaje informativo:** El resultado del sync ahora indica si se uso la extraccion de objetos como fallback

   196→   196→- **Campos:** `salePrice REAL`, `saleStart TEXT`, `saleEnd TEXT` en tabla products

   200→   200→
   201→   201→### Formulas de Precio
   202→   202→```
   203→   203→Precio de lista  = costUSD x (1 + ivaRate/100) x (1 + markup/100) x cotizacionDolar
   204→   204→Precio efectivo  = costUSD x (1 + ivaRate/100) x (1 + (markup - cashDiscount)/100) x cotizacionDolar
   205→   205→Precio oferta    = salePrice (si esta dentro del rango de fechas, reemplaza precio de lista)
   206→   206→```
   207→   207→Donde markup, cashDiscount e ivaRate siguen prioridad: Producto individual → Categoría (heredando de padre si no tiene) → Global/Default.

   286→   286→El PC Builder usa **3 capas de defensa** para garantizar que solo productos correctos aparezcan en cada slot:
   287→   287→
   288→   288→| Capa | Mecanismo | Descripcion |
   289→   289→|------|-----------|-------------|
   290→   290→| **1. Inclusion (Whitelist)** | `BUILDER_INCLUDE_PATTERNS` | Cada slot define que palabras clave DEBE tener el nombre del producto (ej: GPU requiere "RTX/GTX/RADEON"). Si no coincide con NINGUN patron, no aparece. **Es la defensa principal: funciona incluso si la categoria en la DB esta mal** |
   291→   291→| **2. Exclusion (Blacklist)** | `BUILDER_EXCLUDE_PATTERNS` | Patrones que excluyen productos no deseados (notebooks en GPU, discos externos en SSD, etc.) |
   292→   292→| **3. Compatibilidad** | `applyCompatibilityFilters` | Filtra por socket (CPU->Mother), DDR (Mother->RAM), wattaje (GPU->PSU) |
   293→   293→
   294→   294→### Por que se desordenaba antes (Causa raiz resuelta)
   295→   295→El problema recurrente tenia 3 causas encadenadas:
   296→   296→1. **Sync categorizaba mal**: El `CATEGORY_KEYWORD_MAP` chequeaba keywords de componentes (RTX, DDR, SSD) ANTES que productos completos (NOTEBOOK, PC ARMADAS). "NOTEBOOK RTX 4060" coincidia con "RTX" primero -> placas-de-video
   297→   297→2. **PC Builder no validaba nombres**: Solo usaba categoria de DB + blacklist chica. No verificaba que el producto realmente fuera lo que dice la categoria
   298→   298→3. **Cada sync traia productos nuevos mal categorizados**: Aunque corrijas manualmente, la proxima sync "contaminaba" otra vez
   299→   299→
   300→   300→### Solucion permanente (implementada sesion 3)
   301→   301→1. **Whitelist en PC Builder**: `BUILDER_INCLUDE_PATTERNS` - cada slot valida el nombre del producto en runtime
   302→   302→2. **Keywords ordenadas en sync**: Productos completos (NOTEBOOK, PC ARMADAS) se chequean ANTES que componentes (RTX, DDR, SSD)
   303→   303→3. **Validacion post-sync automatica**: Despues de cada sync, se corrigen automaticamente productos mal categorizados en TODAS las categorias del PC Builder

   326→   326→### Deteccion de Socket (FIX sesion 16)
   327→   327→- **Bug:** Intel Core Ultra 5 225F con "LGA1851" (sin espacio) en el nombre era detectado como Socket LGA 1700, bloqueando todas las mothers LGA 1851 compatibles
   328→   328→- **Causa raiz:** El regex `/\bS?1851\b/` no matcheaba "LGA1851" porque `\b` no detecta boundary entre "A" y "1" (ambos son word chars). Al fallar, el fallback asignaba "1700" por defecto a todos los Intel
   329→   329→- **Fix 1 - Regex:** Cambiado a `/(?:S|LGA\s*)?1851/` que matchea S1851, LGA 1851, LGA1851 y 1851 standalone. Mismo fix para 1700
   330→   330→- **Fix 2 - Intel Core Ultra:** Agregada deteccion por modelo: si el nombre contiene "CORE ULTRA", siempre se asigna socket 1851 (Arrow Lake). Se ejecuta antes del fallback a 1700
   331→   331→- **Archivos modificados:** `src/lib/compatibility.ts` (extractProcessorCompatibility + extractMotherboardCompatibility), `src/app/(tienda)/arma-tu-pc/page.tsx` (SLOT_FILTERS regex)

   609→   609→## Protecciones contra Deploy de Versiones Viejas (IMPLEMENTADO sesion 7)
   610→   610→
   611→   611→### Problema que resolvio
   612→   612→Se pusheo una version vieja del codigo que sobreescribio la version correcta en produccion. La causa raiz fue una carpeta `compucity-repo/` duplicada dentro del proyecto que apuntaba al mismo remote de GitHub.
   613→   613→
   614→   614→### Capa 1: Pre-push hook
   615→   615→- **Archivo:** `githooks/pre-push` (configurado via `git config core.hooksPath githooks`)
   616→   616→- **Funcion:** Antes de cada `git push`, verifica que el local no este atras del remoto
   617→   617→- **Si el local esta atras:** Bloquea el push y muestra instrucciones para hacer `git pull --rebase origin main`
   618→   618→- **Si hay divergencia:** Tambien bloquea y sugiere rebase
   619→   619→
   620→   620→### Capa 2: Script de deploy seguro
   621→   621→- **Archivo:** `scripts/deploy.sh`
   622→   622→- **Uso:** `bash scripts/deploy.sh "mensaje del commit"`
   623→   623→- **Verificaciones:** Rama correcta, fetch remoto, comparar commits, verificar cambios pendientes, solo pushea si todo esta OK
   624→   624→
   625→   625→### Capa 3: Eliminacion del repo duplicado
   626→   626→- **Accion:** Se elimino la carpeta `compucity-repo/` que causaba confusion
   627→   627→- **Proteccion:** Se agrego `compucity-repo/` al `.gitignore` para prevenir recrearlo accidentalmente
   628→   628→
   629→   629→### Workflow recomendado
   630→   630→1. Siempre hacer `git pull --rebase origin main` antes de trabajar
   631→   631→2. Hacer cambios, probar localmente
   632→   632→3. Usar `bash scripts/deploy.sh "feat: descripcion"` para pushear de forma segura
   633→   633→4. Vercel se actualiza automaticamente con el push
